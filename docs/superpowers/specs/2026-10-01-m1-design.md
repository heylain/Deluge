# M1: model, A0, and the A1 go/no-go — design

Date: 2026-10-01 · Status: reviewed 2026-10-01, fixes applied, awaiting approval · Branch: `m1`

Brainstormed in `2026-10-01-m1-brainstorm-notes.md`. That file records how each
decision was reached; this one is the spec the implementation plan is written
against. Where they differ, this file wins.

## 1. Goal

M1 is `cfc-hybrid-spec.md` §13's M1, end to end:
1. Build the model.
2. Show that the CfC hybrid trains stably to the loss of a matched transformer
   (A0).
3. Run the A1 arms on the Kaggle chain.
4. Make the go/no-go call.

If CfC does not beat the gated conv by the pre-registered margin (§8.3), text
work freezes and the architecture retargets to audio/event tokens (spec §11).

Done means:
- `docs/results/m1.md` states the A0 and A1 verdicts, produced by
  `scripts/m1_verdict.py` from results the chain exported;
- `cfc-hybrid-spec.md` is updated to match what M1 built.

The project is deliberately slow. Runs are unattended, and calendar time is not
a cost. Nothing below trades rigour for finishing sooner.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | M1 = spec §13 M1 end to end | The go/no-go is the next thing the project needs to know. |
| D2 | A0 before any Triton; no Triton in M1 | A fast kernel for a recurrence that does not train is wasted. Speed only matters at M3, where rented H100 time costs money. |
| D3 | The A0 baseline transformer is our own `Block` stack with an attention mixer in every slot | A nanoGPT would share the harness, data and schedule anyway, so only its forward pass would be independent. That pass is covered by a brute-force attention test (§11). The same config becomes B1 at M3. |
| D4 | Pre-registered noise rule; binding A1 verdict at the dev budget (2.26B tokens), 3 seeds per arm | 500M tokens (4.5 tokens/param, 22% of the dev budget) is an early read only. Rankings that early can flip, and in the direction that favours the conv: a k3 conv learns local statistics fast, while using long-range state is learned later. Three seeds, not two: noise from one seed pair has one degree of freedom, and the 2-seed rule would miss a real 0.02-nat CfC advantage 16–66% of the time, depending on seed noise; three seeds cut that to 3–65% (§8.3). A false no-go pivots the project. |
| D5 | Every M1 run trains at `seq_len` 4096 on long documents (at least 4,097 tokens, §6.1), one document per sequence | At 1024, the stacked 512-token attention windows (blocks 4, 8 and 12 reach ~1,500 tokens) already cover the whole sequence for both arms. A1 would then test only local mixing, where LFM2 found conv ≥ SSM. |
| D6 | λ init is log-uniform: a geometric grid over heads | Read literally, the spec's "a log-uniform" spaces λ linearly: memory 999, 95, 50, … tokens, one long head. The geometric grid gives 999, 655, 429, 281, 184, 120, 79, 52, 34, 22, 14, 9, so half the heads exceed 100 tokens, which is the regime the A1 claim needs. |
| D7 | A gate bias `b_g` in CfC and LRU, init 1.278 | §3 asks for the gate to "start near 1". On zero-mean pre-normed input, `SiLU(W_g x)` averages 0.07 whatever the weights are, so only a bias can do it. SiLU(1.278) = 0.9995, with gradient 1.000. |
| D8 | Results go to the repo, checkpoints to a private Hugging Face repo, both through a separate export workflow that exports each independently | Results are a few KB and belong next to the code that produced them. Checkpoints (~1.3 GB each) do not fit in git. A free HF account has 100 GB of private storage, and M1 needs ~16 GB. Independent, so an HF failure never blocks a verdict. |
| D9 | A0 passes within 2 × noise₀; a stable A0 that trails is diagnosed, then fixed or carried forward as a caveat | At 1 × noise₀, A0 fails 7–23% of the time even when CfC matches the transformer (seed SD 0.005–0.02 nats). At 2 × it fails 0.1–10% and still catches a 0.05-nat deficit at seed SD ≤ 0.01. A0 is a sanity gate and A1 decides the project, so a stable-but-behind A0 must not loop forever. |

## 4. Model

Files follow `docs/project-structure.md`: `deluge/model/{model,block,rope,init}.py`,
`deluge/model/ffn/dense.py` and `deluge/model/mixers/{base,cfc,gated_conv,lru,attention}.py`.
The model imports torch only.

### 4.1 Interfaces

- **Factory:** `deluge.model:build(cfg: ModelConfig) -> nn.Module`, satisfying
  the contract in `deluge/train/trainer.py`'s docstring.
- **`model(inputs, targets)`** returns `(loss, metrics)` with a scalar loss.
- **`model(inputs, targets, reduction="none")`** returns `(token_losses [B,T], stats)`.
  - It goes through `forward` so that `DataParallel` splits it across both GPUs.
  - `stats` maps names to tensors with a leading batch dimension, so the gather
    works:
    - `decay_lambda`: `[B, n_recurrent_layers, H]`, mean λ over the sequence;
    - `state_rms`: `[B, n_recurrent_layers]`, RMS of h at the last position.

    Both keys are absent for arms with no recurrent layers (conv, transformer).
- **`model.no_weight_decay()`** returns parameter *names*.
  - The trainer adds them to its undecayed group, via
    `getattr(model, "no_weight_decay", lambda: ())()` so stub factories still
    work.
  - In practice it moves only the learned conv buffers `[k−1, d_inner]` and the
    sink K/V. Everything else that should be undecayed is already 1-D.
- **Mixers:** `forward(x, state=None, delta=None) -> (y, state)`.
  - `state=None` is a fresh sequence, initialised from the learned h₀ and conv
    buffer, broadcast over the batch.
  - `delta=None` is Δ = 1, and M1 never passes anything else.
  - The returned state is a `MixerState` (`deluge/model/state.py`).
  - Attention accepts only `state=None` and returns `None`: its KV cache is M4.

### 4.2 Mixers

- **CfC.** Exactly spec §3: `v = SiLU(DWConv_k4(W_v x))`,
  `λ = softplus(W_f x + b_f)` per head, `log a = −Δ·λ`, `b = input_scale(log a)`,
  then h is the scan of `(log a, b ⊙ v)` from h₀, and
  `y = W_out(RMSNorm(h) ⊙ SiLU(W_g x + b_g))`.
- **Gated conv (B3), LFM2-style.** `B, C, x̃ = W_in x` (three projections), then
  `y = W_out(C ⊙ DWConv_k3(B ⊙ x̃))`. It has a learned initial conv buffer and
  no recurrent state.
- **LRU (B4).** CfC without the conv and without Δ: `v = SiLU(W_v x)`, with the
  same decay, scan and gated readout, `b_g` included.
  - At A1, Δ is always 1, so the LRU arm measures the conv only. Δ's worth is
    A3's question. Fix the comment in `A1_lru_baseline.yaml`, which claims it
    also measures Δ.
- **Attention** (both the hybrid's A slots and `mixer.type: attention`):
  - GQA with RoPE θ = 1M on Q and K.
  - `n_sink` learned, position-free K/V pairs per KV head, prepended to K/V.
  - SDPA with an explicit boolean mask `[T, n_sink + T]`: sinks are always
    visible, plus the window band `t − W < s ≤ t`. `is_causal` cannot be used,
    because with sinks prepended its top-left alignment is off by n_sink. The
    explicit mask gives up causal block-skipping, so every attention layer costs
    the full T²; the +17% and +70% in §8.2 already assume that.
  - On CUDA, SDPA is pinned to the memory-efficient backend. A silent fallback
    to the math backend would materialise the `[T, n_sink + T]` scores for every
    head and sequence; pinned, it fails loudly instead. The backend in use is
    logged once.
- **Dense FFN.** SwiGLU, `d_ff` from config.

### 4.3 Block and model

- **`Block`** is a pre-norm residual: `x + mixer(norm₁(x))`, then
  `x + ffn(norm₂(x))`.
- **`Model`:**
  1. Embedding.
  2. `n_units` × (C, C, C, A) blocks. C slots use `cfg.mixer`; A slots are
     always attention.
  3. Final RMSNorm, then the tied unembedding.
  4. Cross-entropy in fp32.

### 4.4 Init (`init.py`)

- **`b_f`:** a deterministic geometric grid of λ over heads, from −ln a_max to
  −ln a_min (D6), with `b_f = softplus⁻¹(λ)`. Same grid for the LRU.
- **`W_f`:** zero. The designed decays are then exact at step 0, and `W_f`
  still gets gradient through x.
- **`W_g`:** zero, with `b_g` = 1.278, so the gate is exactly SiLU(1.278) ≈ 1 at
  step 0.
- **Depthwise convs (CfC k4 and gated-conv k3):** identity on the current-token
  tap, which is the spec's "centre tap" read causally. Both arms get the same
  policy, so A1 does not also compare init schemes.
- **h₀ and the learned conv buffers:** zero.
- **Linears and the embedding:** normal, std 0.02. Output projections (`W_out`,
  `W_o`, FFN down) are scaled by 1/√(2 · n_blocks) = 1/√24.

### 4.5 Config changes (`deluge/config.py`)

- **`b_g`:** add `d_inner` to `CfCMixer.params` and `LRUMixer.params`. It is
  1-D, so the trainer's existing rule already leaves it undecayed.
- **The final RMSNorm:** `ModelConfig.params()` gets a `d_model` term for it.
- **`AttentionMixer`**, the `mixer.type: attention` dataclass, with no fields:
  - `state_width = 0` and `uses_delta = False`;
  - `ModelConfig.params()` costs its slots with `_attention_layer_params()`,
    because `mixer.params(d_model)` cannot see the head config. The slots are
    counted under `ParamCount.cfc`, with a comment saying so.
  - One helper costs a mixer layer for both `params()` and `_mtp_params()`, so
    an MTP head on the transformer (M2) cannot call a `params()` that does not
    exist.
  - `ModelConfig` rejects `mixer.type: attention` with non-empty
    `summary_sources`. The C-slot attention layers have no summary projections,
    and costing them as if they did would break the param match.
- **`_check_decay_range` docstring:** state the geometric λ grid (D6).

## 5. Head-batched scan

`deluge/kernels/head_scan.py`:
`head_chunked_scan(log_a [B,T,H], bv [B,T,D], h0 [B,D], chunk) -> (states [B,T,D], h_last [B,D])`,
with D = H · P.

λ is per head, so within a chunk the decay matrix is shared by a head's P
channels. The scan is SSD-style:
1. **Intra-chunk, all chunks at once.**
   - L is the within-chunk cumulative sum of `log_a`.
   - Decay `[B,H,N,C,C]` = exp(L_t − L_s), with the non-causal exponents
     (s > t) set to −∞ *before* the exp. Masking after it is not safe: for
     s > t the exponent is positive, and once a head's decay averages below
     a ≈ 0.24 across a 64-token chunk the exp overflows, and inf × 0 is NaN in
     forward and backward. One short-memory head would then read as "CfC is
     unstable". The reference `chunked_scan` has exactly this bug (NaN at
     λ = 1.5 with chunk 64, where `sequential_scan` is finite); M1 fixes it the
     same way.
   - `within` is one batched matmul against `bv` reshaped to `[B,H,N,C,P]`.
2. **Inter-chunk.** A loop over the N chunks (N = 64 at T = 4096) carries the
   chunk-end state `[B,H,P]` forward, giving `h_chunk_start`. This is cheap next
   to step 1. An `[N,N]` chunk-decay matmul is the optimisation if profiling
   ever says otherwise.
3. **Combine.** `states = within + exp(L_t) · h_chunk_start`.

Other properties:
- **Precision.** fp32 inside, with autocast disabled. Decay is formed as a
  difference of logs, never a ratio, as in `kernels/reference/scan.py`. The scan
  is ~3% of a CfC layer's FLOPs.
- **Memory.** The decay matrix is ~12.6 MB per sequence per layer at T = 4096,
  against `[B,C,C,D]` per chunk in the reference.
- **Δ.** `log_a = −Δ·λ` per token, so MoD gaps (M2) need no change.
- **Chunk.** The mixers call the scan with a fixed chunk of 64. That is tiling,
  not architecture: it is not `cfg.chunk`, the summary chunk, and changing it
  changes nothing but float rounding, memory and speed.
- **Ragged tails.** A ragged final chunk is padded with `log_a = 0` and `bv = 0`,
  which leaves real positions unchanged.
- **No registry.** The mixers import the scan directly. It is pure torch, so
  `project-structure.md` principle 1 holds. The registry arrives with a second
  implementation.

## 6. Data

### 6.1 Preparation (`scripts/prepare_data.py`, new long-document mode)

1. **Measure the yield before fixing any size.** Fineweb-edu rows carry a
   `token_count` column (GPT-2 tokens). Read that column alone across every
   shard of sample-10BT (parquet column projection: tens of MB, not the text).
   That gives the exact GPT-2-token yield of whole 4k pieces without
   tokenizing. Calibrate the GPT-2 → Mistral token ratio on a few thousand
   tokenized documents to convert it. Removing the remainder costs ~2k tokens
   per document on average. If 10BT cannot supply ~2.4B training tokens, use
   sample-100BT; the download is the main cost.
2. **Pre-filter on `token_count`** with a loose threshold, so short documents
   never reach the tokenizer. Then filter exactly: keep documents of at least
   4,097 Mistral-7B tokens. No separator token is written, because a piece never
   spans two documents. The pre-filter threshold is part of the selection rule,
   so provenance records it.
3. **Cut each document into whole pieces of 4,097 tokens** and drop the
   remainder. A piece is 4,097 tokens, not 4,096, because `TokenStream.batch`
   reads `seq_len + 1` tokens (inputs plus shifted targets). With 4,096-token
   pieces, each document's last piece would take a target from the next
   document, inside the [1.5k, 4k) bucket that A1 reads.
4. **Split by document content.**
   - The blake2b hash of the document text, mod 100, sends ~1% of documents to
     held-out and the rest to train.
   - Hashing text rather than index keeps the split stable across re-runs, and
     exact duplicates land on the same side. That matters because FineWeb is not
     deduplicated across dumps.
   - Never use Python's `hash()`.
5. **Write one directory:**
   - `train.bin`: ~2.4B tokens, the 2.26B dev budget plus margin.
   - `heldout.bin`: ~24M tokens, written in hash order so any prefix is a random
     sample of documents.
   - `provenance.json`: dataset name and revision, tokenizer, piece length
     (4,097), the pre-filter threshold, token counts, the split rule, and byte
     sizes.
   
   The output names are explicit, replacing `out.with_suffix(".json")`.
6. **Where it runs.** In a Kaggle CPU kernel with internet: it streams the
   source, tokenizes, and its saved output becomes the dataset. That keeps hours
   of download and tokenizing off the home PC and its shared power bill. A local
   run plus `kaggle datasets create` is the fallback. The result is one new
   private Kaggle dataset of ~4.9 GB, attached to every M1 arm. How a kernel's
   output becomes a private dataset is unverified: check that route first, the
   way `docs/kaggle-chain-spike.md` checked the chain's assumptions, and use the
   fallback if it does not hold.

### 6.2 Reading

- **Piece mode in `TokenStream`.** When the data directory has a
  `provenance.json` with `piece_len`, the stream steps by `piece_len`:
  `n_sequences = len // piece_len`, and sequence i starts at `i · piece_len`.
  Every target then stays inside its piece, and no piece is dropped.
  - Contiguous mode, today's behaviour, is unchanged when there is no
    provenance file (synthetic data, the chain rehearsal).
- **Guard.** The trainer refuses to start if `piece_len != seq_len + 1`.
- **Where the files are found.** `heldout.bin` and `provenance.json` sit next to
  `--data` (`train.bin`), so the chain's `data:` field and `train_command` are
  unchanged.
- **Provenance travels with the run.** The trainer copies `provenance.json` into
  the run directory, so the exporter has it for the HF `run.json` (§9).

## 7. Eval, monitors, and "stable"

### 7.1 Held-out eval

- **Cadence.** `eval_every_tokens` in the train config: 50M for screening and
  100M for dev, which is 190 and 381 steps.
  - These land on checkpoint steps. When both are due, the eval runs before the
    save, so a kill during the eval does not lose the point.
  - `base.yaml` sets it to `null`, because `TrainConfig` rejects a missing key;
    `screen.yaml` and `dev.yaml` override it. `null` disables the in-run evals
    only (see "Completion" below).
  - It stays out of `TrainConfig.fingerprint`, like `checkpoint_every_tokens`.
- **In-run evals** use the first 488 pieces (2M tokens) of `heldout.bin`, a
  random sample of documents (§6.1), and log to `log.jsonl` as `eval` records.
  Readers deduplicate by step, last one wins.
- **Every eval** runs under the training autocast, in batches of `micro_batch`.
- **The final eval** runs once the budget is spent:
  - full-set loss: the binding A1 metric;
  - subset loss, which is free because the subset is inside the full set;
  - loss by position bucket [0, 512), [512, 1536), [1536, 4096);
  - the monitor stats;
  - total and skipped step counts.
  
  It writes `final_eval.json` atomically (temp file + `os.replace`).
- **Completion.**
  - With a `heldout.bin`, the final eval always runs, and `final_eval.json` is
    the completion marker: the trainer exits 0 only once it exists.
  - With no `heldout.bin` (synthetic data, the smoke rehearsals) there is no
    eval of any kind, and completion is today's: budget spent, exit 0.
    Otherwise such runs could never finish.
- **Resume.** A resume that finds the budget spent and no `final_eval.json` runs
  only the eval. That matches how the loop already treats
  `step == total_steps`.
- **Integration.**
  - `loop.py` stays torch-free. It gains the eval cadence the way it has the
    checkpoint cadence, and calls an injected `eval_fn`.
  - The trainer's `eval_fn` runs in `model.eval()` under `no_grad`, restores
    train mode, and touches neither the training RNG nor the data position.

### 7.2 Monitors (spec §7 watch-list)

- **At each eval:** per recurrent layer, the min, median and max across heads of
  a = exp(−mean λ) (the geometric mean of a at Δ = 1), and h RMS.
- **Per log interval:** the fp16 loss scale and the count of skipped steps. A
  skip is detected as the loss scale dropping across `scaler.update()`. The
  cumulative skip count is checkpointed state, restored on resume, so steps
  replayed after a kill are not counted twice.
- `grad_norm` is already logged, and peak GPU memory
  (`torch.cuda.max_memory_allocated`) is added next to `tokens_per_second`.

### 7.3 "Stable"

A run is stable if all four of these hold:
1. **Finite.** The final full-set held-out loss is finite.
2. **No late divergence.** Final subset loss ≤ the best in-run subset loss +
   0.02 nats. This compares the same set to itself. The tolerance is fixed,
   not the noise of §8.3: that noise is computed from the very CfC runs being
   judged, so a late-diverging run would inflate it and pass its own check.
3. **No decay collapse**, judged on the final eval's stats. In no layer are all
   heads below a = 0.5 (amnesia) or all above 0.9999. Above 0.9999 is a memory
   of ~10k tokens, longer than the sequence, where b = √(1−a²) ≈ 0.014 and the
   layer barely reads its input. λ is unbounded both ways, so both thresholds
   can fire.
4. **Few skipped steps.** At most 1% of steps are skipped by the fp16 scaler.
   Past that, arms are no longer matched on update count. The count is reported
   for every run regardless.

These are deliberately loose: they catch breakage, not mediocrity. A broken but
finite run fails the A0 loss comparison anyway.

Stability is judged first, with these fixed thresholds only. §8.3's noise is
then computed from stable runs only.

## 8. Experiments

### 8.1 Configs

- **`configs/train/base.yaml`:**
  - `seq_len: 4096`.
  - `global_batch_tokens` stays 262,144, now 64 sequences, so the step count
    and the LR schedule are unchanged.
  - `eval_every_tokens: null` (§7.1).
  - `micro_batch` is set from the local smoke run (§11): the largest per-GPU
    power of two whose peak reserved memory on the 5070 Ti stays at or under
    ~13 GiB (a T4 has ~14.7 GiB usable, and the 5070 Ti also drives the
    display). DataParallel splits `micro_batch` across the two T4s, so it is
    twice that value. It must divide the 64 sequences of a step, so even is not
    enough.
  - Fix the stale comments ("256 sequences of 1024", "32 accumulation steps").
  - `smoke.yaml` keeps `seq_len: 64`.
- **`configs/train/screen.yaml` and `dev.yaml`** set `eval_every_tokens`.
- **New train configs**, each extending its budget and setting only `seed`:
  - `screen_seed2.yaml` and `dev_seed2.yaml`: `seed: 4321`;
  - `dev_seed3.yaml`: `seed: 7777`.
  - Not 1235: the stream keys epochs as `seed + epoch`, so adjacent seeds share
    orderings across epochs. 1234, 4321 and 7777 share no key within 100 epochs.
  - Same seed means the same data order, so arms on the same seed are paired on
    data. (Init differs between architectures whatever the seed.) Another seed
    changes both data order and init, which slightly overstates the noise of a
    paired comparison: the A1 bar gets stricter, and A0's tolerance looser.
- **`configs/train/rehearse.yaml`** (batch 0, §8.2) extends `screen.yaml`:
  80 steps (20,971,520 tokens), 10 of warmup, a checkpoint every 20 steps and an
  eval every 40, so the save, the in-run eval and the final eval all run.
- **Model configs:**
  - `A0_scan_only.yaml` (CfC): unchanged except its header comment, which calls
    A0 "the stability check, not a quality comparison". It is now also the
    comparison against the transformer, and the CfC arm of A1.
  - `A0_transformer_baseline.yaml`: new.
  - `A1_conv_baseline.yaml` and `A1_lru_baseline.yaml`: re-based on
    `A0_scan_only.yaml`, so window-only, as spec §11 puts summaries at A2.

sets `export: true` (§9) and uses `data: heylaine/deluge-long4k:train.bin`. The
slug is final once the dataset is created.

### 8.3 Pre-registered rules

Fixed here, before any result exists. The metric is final full-set held-out
loss in nats. Stability (§7.3) is judged first, with fixed thresholds only; the
noise below is computed from stable runs only.

- **A0 noise:** noise₀ = max(|CfC s1 − CfC s2|, 0.01), from
  `m1-a0-cfc-s1/s2`. This estimates the standard deviation of the difference
  between two single runs. The floor stops a lucky close pair from setting the
  bar too low.
- **A0 passes** iff:
  - both CfC runs and the transformer are stable (§7.3), and
  - CfC s1 − transformer ≤ 2 × noise₀, i.e. CfC is within two estimated
    standard deviations or better. Both runs use seed 1234, so they are paired
    on data.

  Simulated with independent normal seed noise, this fails a CfC that truly
  matches the transformer 0.1% / 4% / 10% of the time at a seed SD of
  0.005 / 0.01 / 0.02 nats, and catches a true 0.05-nat deficit 100% / 89% /
  58% of the time. At 1 × noise₀ the false-fail rate would be 7% / 18% / 23%.
- **A0 stable but behind** (all three runs stable, CfC s1 − transformer >
  2 × noise₀): diagnose before rerunning anything.
  - Position buckets: a gap concentrated in [1536, 4096) points at long-range
    state; a gap spread evenly points at init or optimisation.
  - The decay monitors and the gate statistics.
  - A bug found: fix it, and rerun batch 1 under new names.
  - No bug found: queue batch 2, and report the A0 gap and the diagnosis as a
    caveat. A1, not A0, decides the project.
- **A0 unstable:** debug, fix, and rerun under new names.
- **Early A1 read (not binding):** conv − CfC at seed 1234, reported in units of
  noise₀. It triggers nothing. The LRU arm is reported the same way, as the
  conv's worth.
- **Binding A1 verdict** (the dev budget, all six runs stable):
  1. s = the sample standard deviation (n − 1) of the three CfC losses, and
     noise = max(√2 · s, 0.01). Like noise₀, it estimates the standard
     deviation of the difference between two single runs; with two seeds it
     would be |d1 − d2|.
  2. gap = mean(conv d1, d2, d3) − mean(CfC d1, d2, d3). Positive means CfC is
     better.
  3. **GO** iff gap ≥ 2 · noise / √3 (≈ 1.155 · noise), else **NO-GO**. A
     3-vs-3 mean gap has standard deviation σ·√(2/3) = noise/√3, so the bar is
     two *estimated* standard errors.
  4. There are no extension runs.
- **What the rule does.** The noise is an estimate with two degrees of freedom,
  not a known quantity, so the rule's error rates are not those of two exact
  standard errors. Simulated with independent normal seed noise:

  | seed SD | P(GO), true gap 0 | 0.01 | 0.02 | 0.03 |
  |---|---|---|---|---|
  | 0.005 | 0.00 | 0.33 | 0.97 | 1.00 |
  | 0.01 | 0.04 | 0.28 | 0.67 | 0.91 |
  | 0.02 | 0.08 | 0.19 | 0.35 | 0.53 |

  When the floor binds (seed SD ≲ 0.005), the rule is in effect "CfC wins by at
  least 0.0115 nats". With two seeds the 0.02 column would read 0.84 / 0.54 /
  0.34, which is why D4 runs three. A NO-GO therefore means "no advantage this
  design can see", not "no advantage".
- **If any binding run is unstable,** there is no verdict. Debug, fix, and rerun
  under new names. Instability is not a no-go.
- **Outcome:** GO leads to M2. NO-GO leads to spec §11's pivot. In both cases the
  position buckets are reported, to show where the gap does or does not come
  from.

## 9. Export: results to the repo, checkpoints to Hugging Face

The chain's state machine (`deluge/chain/step.py`) gains two fields and nothing
else. A separate workflow does the exporting, so the 15-minute tick job never
waits on a multi-GB transfer.

**Changes to the chain:**
- **`runs.yaml`:** an optional `export: bool`, default false, validated in
  `queue.py`. The rehearsal history is never exported.
- **The done record** (`step.py` `_record`) gains:
  - `side`: the kernel that ran the last session;
  - `export`: copied from the run entry.

**`.github/workflows/export.yml`:**
- Hourly cron and `workflow_dispatch` only (no `pull_request`, so the secrets are
  never reachable from a fork's code), master only as in `chain.yml`, its own
  concurrency group, a 60-minute timeout, and `contents: write`.
- Secrets: `KAGGLE_USERNAME`, `KAGGLE_KEY`, `HF_TOKEN`.
- It runs `python -m deluge.chain.export`, which is idempotent. The work is
  derived from the repo, with no ledger. For each `done` record with
  `export: true` and not skipped, two independent steps, each skipped once its
  marker exists:
  1. **Results** (marker: `docs/results/runs/<name>/final_eval.json`). From
     kernel `deluge-<name>-<side>`, fetch `final_eval.json` and `log.jsonl` with
     `kernels output --file-pattern`, as `fetch_session_json` already does.
     Write into `docs/results/runs/<name>/`:
     - `final_eval.json`;
     - `evals.csv`, from the deduplicated eval records;
     - `train.csv`, the step records deduplicated and downsampled to ~500 rows:
       loss, lr, loss scale, skips, grad norm, tokens per second, peak memory.

     Commit at once, with the chain's existing `pull --rebase` and push retry.
     A verdict never waits on the checkpoint.
  2. **Checkpoint** (marker: `docs/results/runs/<name>/export.json`). Fetch the
     newest `step-*.pt` (`keep_last: 2` means two are present, ~2.6 GB on a
     runner with ~14 GB free). Upload it to the private HF model repo named in
     `configs/chain/export.yaml` (`hf_repo: <user>/deluge-runs`), at
     `<name>/step-N.pt`, with the full `log.jsonl` and a `<name>/run.json` (the
     run entry, the commit, and the data provenance the trainer copied into the
     run directory, §6.2). The repo is created private if missing. Then write
     `export.json` (HF repo, path, sha256, size, source kernel) and commit it
     the same way.
- **On failure.** A failed step writes nothing, so the next hourly run retries
  it. The workflow fails, which emails the user by the chain's alert path, only
  once a run has been done for more than ~3 h without its exports, judged from
  the done record's `finished`. A transient Kaggle or HF error retries quietly.
  The documented manual fallback stays:
  `kaggle kernels output <user>/deluge-<run>-<side> -p out/`.

The full checkpoint is uploaded (fp32 weights, Adam moments, scaler and RNG), so
a run can be continued or re-evaluated later. Twelve runs (eleven M1 runs and the
rehearsal) come to ~16 GB of the 100 GB free private quota. Pruning screening
checkpoints is a later decision.

## 11. Testing

All on CPU unless marked. New tests:

- **Scan** (`test_head_scan.py`):
  - parity with `sequential_scan` forward and backward, with per-head `log_a`
    expanded via `repeat_interleave`;
  - chunk sizes {1, 16, 64}, a ragged final chunk, and long-chunk underflow;
  - strong decay (λ = 5 across a 64-token chunk) stays finite forward and
    backward and matches `sequential_scan`, for `head_chunked_scan` and for the
    fixed reference `chunked_scan` (a new case in `test_scan_parity.py`).
- **Mixers:**
  - each recurrent or conv mixer gives the same output when a sequence is run
    whole or split in two, carrying state across the split;
  - attention matches a brute-force reference (naive softmax(QKᵀ)V with an
    explicit sink + window mask) for windows below and at T. D3 rests on this
    test, so the reference shares no helper with the module: it applies RoPE in
    complex form and expands KV heads by explicit indexing;
  - RoPE alone: q·k depends only on t − s.
- **Model:**
  - the instantiated model's parameter count equals `cfg.params().total` for all
    four arms;
  - a fresh model's loss is ≈ ln 32000 + σ²/2 ≈ 10.5, where σ ≈ 0.55 is the
    logit SD a tied std-0.02 embedding gives (tolerance ~0.3);
  - a tiny model overfits one batch;
  - `reduction="none"` returns `[B,T]` losses whose mean equals the scalar loss,
    and `stats` have a leading batch dimension;
  - the names from `no_weight_decay()` land in the trainer's undecayed group,
    and a factory without the method still works (`test_torch_backend.py`).
- **Init:**
  - exp(−softplus(b_f)) equals the geometric a grid exactly;
  - the gate equals SiLU(b_g) at step 0;
  - both convs are the identity on the last tap.
- **Config invariants:**
  - the A1 arms differ from A0 only in the mixer;
  - the A1 arms and the transformer are within 0.5% of A0;
  - the transformer differs from A0 only in mixer, window and `d_ff`;
  - `mixer.type: attention` with non-empty `summary_sources` is rejected.

  The first two replace `test_ablation_configs_differ_from_dev_only_in_the_mixer`
  and `test_a1_arms_are_parameter_matched_to_the_cfc_arm`, which compare against
  `dev.yaml` and fail once the arms are re-based.
- **Existing tests that change:**
  - `test_screen_and_dev_differ_only_in_the_budget` counts `eval_every_tokens`
    as a budget field;
  - the `TrainConfig` fixtures (`make()` in `test_train_config.py`, `BUDGET` in
    `test_torch_backend.py`, the config in `test_resume.py`) gain
    `eval_every_tokens`.
- **Data:**
  - in piece mode every target stays inside its piece and no piece is dropped;
  - contiguous mode is unchanged;
  - the guard rejects `piece_len != seq_len + 1`;
  - the trainer copies `provenance.json` into the run directory;
  - the prep split is deterministic, and duplicates land on the same side.
- **Eval:**
  - `test_resume`: eval calls move neither the step count nor the data position;
  - a resume with the budget spent runs only the final eval;
  - the exit code is 0 only once `final_eval.json` exists;
  - with no `heldout.bin`, the run exits 0 once the budget is spent, as today;
  - the skip count survives a resume without counting replayed steps twice.
- **Eval, torch-level** (`test_torch_backend.py`): N steps with an eval every
  step and N steps with none give bit-identical weights and optimizer state.
- **Chain:**
  - `export` is validated in the queue;
  - the done record carries `side` and `export`;
  - the exporter's selection logic: which records it exports and which it
    skips, with the results and checkpoint steps keyed on their own markers;
  - the ~3 h grace before an export failure fails the workflow;
  - the existing rehearsal tests pass unchanged.
- **Verdict:** the rules at their boundaries:
  - the floor, exactly 2 × noise₀ for A0, and exactly 2 · noise / √3 for A1,
    with s the n − 1 sample SD;
  - each §7.3 criterion: a non-finite loss, the 0.02-nat late-divergence bound,
    a layer with all heads below a = 0.5 or all above 0.9999 (and one with heads
    on both sides, which passes), and the 1% skip bound;
  - an unstable run settles the outcome before any noise is computed: A0
    unstable, or no A1 verdict;
  - the A0 "stable but behind" outcome is distinguished from a fail.
- **Local smoke, 5070 Ti, not CI.** Each of the four arms at `seq_len` 4096, in
  fp16 as on the T4, on `heldout.bin` and `provenance.json` downloaded from the
  Kaggle dataset (~50 MB) and passed as `--data`. It uses `rehearse.yaml`
  (80 steps), so each arm runs to completion and the in-run eval, the final
  eval, `final_eval.json` and exit 0 all run. It settles the per-GPU
  `micro_batch` (§8.1) and logs peak memory before anything is queued. What it
  cannot exercise (two GPUs, the T4, the dataset mount, the export) is batch 0's
  job.

## 12. Manual steps for the user

1. Create a Hugging Face token that can write and create repos in your
   namespace. Add it as the GitHub secret `HF_TOKEN`, and set `hf_repo` in
   `configs/chain/export.yaml`. This must be in place before batch 0.
2. Run, or approve running, the data prep (§6.1), and publish the long-document
   dataset to Kaggle by whichever route §6.1 step 6 verified.
3. Download `heldout.bin` and `provenance.json` from it for the local smoke.
4. Merge `m1` into `master` once tests and the local smoke pass.
5. Queue batch 0, and check its pass list (§8.2).
6. Queue batch 1. Read the A0 verdict, and the diagnosis if A0 trails (§8.3).
   Queue batch 2 if A0 passes or is carried forward.

## 13. Risks and open items

- **Data yield** (§6.1) is measured first, and its result fixes the dataset
  sizes.
- **Memory at 4096 on a T4.** The local smoke settles `micro_batch`. If even
  `micro_batch` = 2 (one per GPU) does not fit, the first lever is the loss:
  the fp32 cross-entropy over the 32k vocab is ~1–1.5 GB per 4,096-token
  sequence, and computing it in sequence chunks recovers most of that.
  Activation checkpointing per block comes after, decided then.
- **fp16 at 4096.** The scan is fp32 internally. Any overflow shows up in the
  skip count (§7.3.4).
- **Throughput is unmeasured.** Batch 0 gives a first T4 number and A0's first
  session a full one. Nothing in the design depends on the guess.
- **Seed noise is unmeasured.** The binding rule's power depends on it (§8.3's
  table). A0's two CfC runs give a first estimate, at the screening budget.
- **HF quota.** M1 uses ~16 GB of 100 GB. Later milestones will need pruning or
  PRO.
